# Component Library vs Core Widgets

Web 项目里常有 Component Library，比如：

```text
Button
Card
Dialog
Input
Tabs
ProductCard
EmptyState
```

Flutter 项目里通常对应两层：

```text
Flutter/Material 内置 Widgets
项目自己的 Core Widgets
```

可以这样映射：

| Web Component Library    | Flutter                                    |
| ------------------------ | ------------------------------------------ |
| UI library components    | Material/Cupertino Widgets                 |
| shared components        | `core/widgets`                             |
| design system components | App Core Widgets + Theme                   |
| Button                   | `ElevatedButton` / custom AppButton        |
| Card                     | `Card` / custom AppCard                    |
| Dialog                   | `AlertDialog` / custom dialog              |
| Input                    | `TextField` / `TextFormField`              |
| Empty State              | custom `EmptyState` Widget                 |
| Loading Skeleton         | custom skeleton Widget                     |
| Product Card             | feature/core Widget                        |
| Storybook                | Widgetbook / custom preview / widget tests |

---

## 1. Web Component Library

Web 中常见结构：

```text
src/components/
  Button.tsx
  Card.tsx
  Dialog.tsx
  EmptyState.tsx
  ProductCard.tsx
```

或者更系统化：

```text
src/design-system/
  button/
  input/
  modal/
  typography/
```

作用是：

```text
统一 UI 样式
复用交互模式
减少重复代码
沉淀业务组件
```

---

## 2. Flutter Core Widgets

Flutter 项目中常见：

```text
lib/core/widgets/
  app_button.dart
  empty_state.dart
  error_view.dart
  loading_skeleton.dart
  product_card.dart
```

`core/widgets` 通常放：

```text
跨业务复用
和具体 feature 解耦
具备项目视觉规范
多个页面都会用
```

比如：

```dart
EmptyState(...)
ErrorView(...)
AppImage(...)
AppConfirmDialog(...)
```

---

## 3. Material Widgets vs App Widgets

Flutter 自带很多 Material 组件：

```text
ElevatedButton
TextButton
Card
Dialog
TextField
Checkbox
Switch
BottomNavigationBar
NavigationBar
AppBar
SnackBar
```

项目 Core Widgets 通常不是替代全部 Material，而是在它们之上封装项目规范：

```dart
class AppButton extends StatelessWidget {
  const AppButton({
    super.key,
    required this.onPressed,
    required this.child,
  });

  final VoidCallback? onPressed;
  final Widget child;

  @override
  Widget build(BuildContext context) {
    return ElevatedButton(
      onPressed: onPressed,
      child: child,
    );
  }
}
```

---

## 4. Core Widget vs Feature Widget

建议区分：

| 类型           | 放哪里                                | 示例                                  |
| -------------- | ------------------------------------- | ------------------------------------- |
| 跨业务通用     | `lib/core/widgets`                    | `EmptyState`, `AppImage`, `ErrorView` |
| 业务领域组件   | `lib/features/*/presentation/widgets` | `OrderCard`, `CartSummary`            |
| 页面私有小组件 | 当前 page 文件或同目录                | `_Header`, `_FilterBar`               |
| 设计基础组件   | `core/widgets` / `core/theme`         | `AppButton`, `AppTextField`           |

判断标准：

```text
多个 feature 都会用，放 core；
只属于某个业务，放 feature；
只属于一个页面，先留在页面附近。
```

---

## 5. 不要过早抽成 Core Widget

Web 中容易把所有东西都放进 `components/`。

Flutter 也一样，不要一开始就把页面里的所有小块都抽到 `core/widgets`。

更好的顺序：

```text
先在页面内实现
第二次复用时提到 feature widgets
跨 feature 复用时再提到 core/widgets
```

避免：

```text
core/widgets 变成大杂烩
组件依赖具体业务模型
通用组件越来越难改
```

---

## 6. Core Widget 应该保持清晰边界

好的 Core Widget：

```text
参数明确
不依赖某个具体页面
不直接访问业务 repository
不偷偷读取过多全局状态
视觉和行为稳定
容易写 widget test
```

不好的 Core Widget：

```text
名字很通用但逻辑很业务
内部根据很多 feature 状态分支
参数过多
隐藏网络请求
难以单独预览和测试
```

## 7. 当前项目心智

如果项目已有类似：

```text
lib/core/widgets/product_card.dart
lib/core/widgets/empty_state.dart
lib/core/widgets/error_view.dart
lib/core/widgets/loading_skeleton.dart
lib/core/widgets/app_image.dart
```

可以理解为：

```text
这些就是 Flutter 项目里的共享组件库。
```

后续页面开发应优先复用这些 Core Widgets，而不是每个页面重新写一套空状态、错误态、图片加载和卡片样式。

---

一句话理解：

```text
Web Component Library 是项目共享组件体系；
Flutter Core Widgets 是同样的角色，
通常建立在 Material/Cupertino Widgets 之上，
沉淀项目通用视觉、交互和业务 UI 模式。
```
